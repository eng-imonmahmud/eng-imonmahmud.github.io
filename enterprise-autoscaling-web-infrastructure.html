Enterprise Auto-Scaling Web Infrastructure on Google Cloud Platform

Project Overview

This repository contains a complete, production-grade Infrastructure as Code (IaC) deployment for a highly available, auto-scaling web application on Google Cloud Platform. Built entirely with Terraform, the project automatically provisions a secure, robust foundation featuring a Global External HTTP Load Balancer distributing traffic across a Managed Instance Group of OpenLiteSpeed web servers, connected securely to a private Cloud SQL database.

Business Objective

To design and implement an enterprise-grade cloud architecture that guarantees zero downtime during traffic spikes through horizontal scaling, ensures strict security via private IP networking and least-privilege IAM, and minimizes operational overhead by leveraging fully managed GCP services and Infrastructure as Code automation.

Key Features

  • High Availability & Scalability: Auto-scaling Managed Instance Group (MIG) that dynamically adjusts computing resources based on CPU utilization.
  • Global Traffic Routing: Global HTTP Load Balancer equipped with Google's premium network tier for low latency and high throughput.
  • Zero-Touch Provisioning: Automated deployment of the OpenLiteSpeed web server using compute instance startup scripts.
  • Robust Security: Compute instances have no external IPs, communicating exclusively via Cloud NAT. Database connectivity is secured through Private Services Access.
  • Least-Privilege Identity: Custom IAM service account restricted strictly to required roles (Cloud Logging, Monitoring, Cloud SQL Client).
  • Comprehensive Observability: Full integration with Google Cloud Operations Suite (Cloud Logging and Cloud Monitoring).

    Infrastructure Components

    Terraform Module Structure

    The infrastructure is completely modularized for reusability and clean state management:

  • networking: Provisions the custom VPC, Subnet, Private Services Access, Cloud NAT, and precise Firewall rules allowing health checks and SSH via Identity-Aware Proxy (IAP).
  • compute: Deploys the Instance Template with the OpenLiteSpeed automated startup script, Managed Instance Group, HTTP Health Check, and Auto Scaling policy.
  • database: Provisions a highly secure Cloud SQL MySQL instance configured strictly with a Private IP (no public endpoint).
  • loadbalancing: Deploys the Global Forwarding Rule, Target HTTP Proxy, URL Map, and Backend Service.
  • iam: Sets up the restrictive custom Service Account.

    Deep Dive Explanations

    Auto Scaling

    The environment utilizes a Google Compute Region Autoscaler configured with a target CPU utilization of 70%. When traffic spikes cause the average CPU load to exceed this threshold, the autoscaler dynamically provisions new instances up to the configured maximum, ensuring responsive performance under heavy load.

    Load Balancer

    The Global External HTTP Load Balancer serves as the single point of entry. It evaluates incoming traffic and forwards it to the closest healthy backend instance based on the configured HTTP Health Check, effectively masking the underlying infrastructure details and preventing single points of failure.

    Cloud SQL

    A Cloud SQL MySQL database is provisioned to act as the persistent data store. Security is prioritized by completely disabling public IP mapping. All communication between the web servers and the database occurs over the internal Google network via Private Services Access.

    Networking & Security

    A custom VPC is deployed with a dedicated subnet. Compute instances reside entirely within private IP space. Outbound internet access required for software installation (OpenLiteSpeed) is facilitated through a Cloud NAT gateway attached to a Cloud Router. Firewall rules strictly allow ingress only from Google's health check IP ranges.

    IAM (Identity and Access Management)

    A dedicated custom Service Account (enterprise-compute-sa) is assigned to the compute instances. It restricts the instances to write logs, emit monitoring metrics, and connect to Cloud SQL, strictly adhering to the principle of least privilege.

    Validation & Testing Process

    Following deployment, the automated workflow performs strict validation:

    1. Polls the Load Balancer IP over HTTP.

    2. Waits for Google's global DNS and routing propagation to complete.

    3. Evaluates the HTTP response to confirm an HTTP 200 OK status.

    4. Verifies the specific HTML signature of the OpenLiteSpeed landing page.

    Cost Considerations

    To optimize costs for this architecture:

  • e2-micro instances are utilized for the compute tier.
  • db-f1-micro is chosen for the database tier.
  • The autoscaler is constrained to minimize unnecessary expansion during idle periods.

    • Challenges and Solutions

  • Challenge: Google Cloud Global Health Checks enforce eventual consistency, sometimes causing a resourceNotReady failure when linking the Backend Service immediately after Health Check creation.
  • Solution: Automated the deployment pipeline to elegantly catch the failure and autonomously re-trigger the apply command, successfully resolving the dependency tree.
  • Challenge: OpenLiteSpeed listens on port 8088 by default, which breaks standard port 80 load balancer health checks. Modifying complex configuration files automatically during startup is brittle.
  • Solution: Implemented an immediate iptables NAT PREROUTING rule in the startup script to seamlessly redirect port 80 traffic to 8088, ensuring rock-solid health checks without altering complex application configs.

    • Future Improvements

  • Implement HTTPS/SSL using Google-managed SSL certificates on the Load Balancer.
  • Integrate Cloud Armor for advanced WAF (Web Application Firewall) protection and DDoS mitigation.
  • Store the Terraform state remotely in a Google Cloud Storage bucket with state locking via Cloud KMS.
