Automated Cloud Observability & Self-Healing Incident Response System

📌 Professional Overview

This project demonstrates a fully automated, event-driven, self-healing cloud infrastructure entirely within AWS. Designed with enterprise-grade cloud engineering principles, the system continuously monitors an EC2 workload for anomalies. Upon detecting critical CPU exhaustion, it autonomously triggers an event-driven remediation workflow to recover the instance—requiring zero human intervention.

This robust incident response architecture leverages Infrastructure as Code (IaC) for reproducible deployments, strict Least Privilege IAM roles for security, and Serverless computing for cost-efficient operations.

    🌟 Key Features

  • Infrastructure as Code (IaC): 100% of resources provisioned seamlessly via Terraform.
  • Event-Driven Resilience: CloudWatch metrics seamlessly invoke EventBridge rules.
  • Automated Remediation: AWS Lambda executes Python (Boto3) scripts to autonomously recover degraded instances.
  • Strict Security Posture: Follows IAM Least Privilege principles. Instances are isolated with no open inbound ports; all access is securely routed via Systems Manager (SSM).
  • Cost-Optimized Architecture: Architected to run entirely within the AWS Free Tier bounds without sacrificing reliability.

    🏗 Architecture Overview

    The system utilizes an event-driven self-healing pattern.

    mermaid
    flowchart TD
    A[EC2 Instance\nWorkload] -->|Emits Metrics| B(CloudWatch Metrics)
    B -->|CPU > 90%| C(CloudWatch Alarm)
    C -->|State Change:\nALARM| D{EventBridge Rule}
    D -->|Invokes| E[AWS Lambda\nPython/Boto3]
    E -->|Executes Reboot| A
    E -->|Writes Logs| F[CloudWatch Logs]

    Event Flow & Workflows

    1. Monitoring Workflow: EC2 natively streams metric telemetry to CloudWatch.

    2. Validation Workflow: A stress-test script (stress-ng) is securely injected via Systems Manager (SSM) to artificially spike CPU usage.

    3. Self-Healing Workflow: CloudWatch triggers an Alarm -> EventBridge catches the state transition -> Lambda dynamically retrieves the impacted instance and issues an EC2 Reboot command.

    🔒 Security Considerations & IAM Least Privilege Summary

  • No Hardcoded Secrets: Zero AWS credentials or sensitive configurations exist in the repository. A rigorous .gitignore prohibits tfstate leaks.
  • Compute Security: EC2 instance has an empty Ingress Security Group. There is no SSH access.
  • SSM Role: EC2 assumes the AmazonSSMManagedInstanceCore policy solely for secure remote management.
  • Lambda Role: Bound strictly to ec2:RebootInstances and ec2:DescribeInstances alongside CloudWatch logging permissions (logs:CreateLogStream, logs:PutLogEvents).

    🚀 Deployment & Testing Procedure

    1. Deployment Workflow

    bash
    cd terraform
terraform init
terraform validate
terraform apply -auto-approve

    2. Testing Procedure (Validating Self-Healing)

    Using AWS CLI to securely execute the stress test via Systems Manager:

    bash
    aws ssm send-command \
  --instance-ids "<YOUR_INSTANCE_ID>" \
  --document-name "AWS-RunShellScript" \
  --parameters '{"commands":["stress-ng --cpu 4 --timeout 300s --metrics-brief"]}' \
  --region eu-central-1

    3. Validation Results

  • The CPU gracefully spikes above 90%.
  • The CloudWatch Alarm transitions to ALARM.
  • EventBridge triggers Lambda instantly.
  • Lambda reboots the instance, bringing metrics back to healthy (OK) parameters.

    🔮 Project Highlights & Future Enhancements

  • Highlights: Achieved full IaC deployment coupled with reactive, agentless security controls resulting in a highly resilient architecture.
  • Future Enhancements:
  • Introduce Amazon SNS to alert administrators via Email/SMS when auto-remediation triggers.
  • Implement Auto Scaling Groups (ASG) to completely terminate and replace instances instead of rebooting.
  • Migrate Terraform state to a remote S3 backend with DynamoDB state locking.

    • 🧠 Lessons Learned

  • Event-Driven Paradigms: Decoupling monitoring (CloudWatch) from compute execution (Lambda) using EventBridge significantly reduces system coupling and increases reliability.
  • SSM Superiority: Leveraging Systems Manager eliminated the risks associated with Bastion Hosts, exposed SSH keys, and public IP requirements.
